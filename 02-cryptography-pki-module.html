Cryptography Fundamentals
Goals, vocabulary, and the core properties every system must achieve
Foundation

What Cryptography Solves

Cryptography is the science of protecting information through mathematical transformations. It does not hide data by obscuring its location — it transforms data so that only authorized parties can understand it. Modern cryptography rests entirely on computational hardness: certain mathematical problems are easy in one direction but computationally infeasible to reverse.

Five security goals that cryptography addresses: Confidentiality (only authorized parties read the data), Integrity (data has not been modified), Authentication (parties are who they claim), Non-repudiation (sender cannot deny sending), and Availability (indirectly — protecting systems from cryptographic bypass).

Plaintext
The original, readable data before any cryptographic transformation. Also called cleartext. Example: your password "admin123" before hashing.
Ciphertext
Encrypted, unreadable output produced by applying a cipher to plaintext. Meaningless without the decryption key. Secure even if intercepted.
Cipher
The algorithm that performs encryption and decryption. Examples: AES, RSA, ChaCha20. Different ciphers have different performance, security, and use-case profiles.
Key
A secret value that controls the cipher's transformation. Same algorithm + different key = different ciphertext. Security comes from key secrecy, not algorithm secrecy (Kerckhoffs' principle).
Kerckhoffs' Principle
"A cryptosystem should be secure even if everything about the system, except the key, is public knowledge." The algorithm must be open to scrutiny. Security through obscurity does not work.
Entropy
Measure of randomness/unpredictability in a key or password. High entropy = more secure. 256-bit random key has astronomical entropy; "password1" has near-zero.

Historical Context — Why Algorithms Were Broken

Caesar Cipher (50 BC): Shift each letter by a fixed amount. Key space = 25. Broken by frequency analysis — the letter 'e' appears most often in English regardless of shift.

DES (1977): 56-bit key. Broken in 1997 by EFF's Deep Crack in 22 hours by brute force. Key space was too small for modern computing. Retired, replaced by AES.

MD5 (1992): Collision attacks found in 2004 (Wang & Yu). Two different inputs can produce the same hash — catastrophic for digital signatures. Do not use for security.

Lesson: Cryptographic algorithms don't last forever. Always use current recommended algorithms and key sizes.

II
Symmetric Encryption
AES, modes of operation, block vs stream ciphers, and key management
Encryption

Symmetric Encryption — One Key for Both Parties

In symmetric encryption, the same key is used to encrypt and decrypt. Both Alice and Bob must possess the identical secret key before any communication begins. This is extremely fast — AES can encrypt gigabytes per second on modern hardware — but has one fundamental problem: key distribution. How do Alice and Bob securely share the key in the first place without an attacker intercepting it?

This key distribution problem is what asymmetric cryptography and key exchange protocols solve. In practice, symmetric encryption does the heavy lifting of bulk data encryption, while asymmetric cryptography is used only to securely exchange the symmetric key.

Symmetric encryption model Encrypt: C = EK(P)  ·  Decrypt: P = DK(C)  ·  Same K for both
AES-128
128-bit key, 10 rounds. Currently unbroken. Best known attack requires 2126.1 operations. Sufficient for most use cases including TLS data encryption.
AES-256
256-bit key, 14 rounds. Double the key length. Recommended for top secret and long-term data protection. Slightly slower than AES-128. Required by many compliance frameworks.
3DES (Triple DES)
Applies DES three times: EK1(DK2(EK3)). Effective key size 112 bits. Legacy only. NIST deprecated 2017. Should not be used in new systems.
ChaCha20
Stream cipher, software-optimized. Used when AES hardware acceleration unavailable (mobile, IoT). Paired with Poly1305 for AEAD — ChaCha20-Poly1305. Used in TLS 1.3.
Block Cipher
Encrypts fixed-size blocks (AES: 128 bits). Needs a mode of operation to handle data longer than one block. Mode determines security properties beyond the block size.
Stream Cipher
Encrypts data bit-by-bit/byte-by-byte using a keystream XORed with plaintext. No padding needed. Fast for real-time data. Examples: RC4 (broken), ChaCha20 (secure).

AES Modes of Operation — Critical for Security

The mode determines how AES is applied to data longer than one 128-bit block. The choice of mode dramatically affects security, even when using the same key.

ModeFull NamePropertiesUse CaseSecurity
ECB Electronic Codebook Each block encrypted independently with same key. No IV needed. Almost never — only single-block data Broken — same plaintext = same ciphertext. Reveals patterns (ECB penguin attack).
CBC Cipher Block Chaining Each block XORed with previous ciphertext before encrypting. Requires IV. File encryption, disk encryption (old) Secure if IV is random and unpredictable. Vulnerable to BEAST, padding oracle if misused.
CTR Counter Mode Converts block cipher into stream cipher using an incrementing counter. Parallelizable. Disk encryption, streaming data Secure. Never reuse nonce+key pair — catastrophic if repeated.
GCM ★ Galois/Counter Mode CTR mode + GHASH authentication tag. AEAD — provides both encryption AND integrity. TLS 1.2/1.3, HTTPS, storage encryption Best choice for most applications. Used in AES-256-GCM (TLS 1.3 cipher suite).
💡 AEAD (Authenticated Encryption with Associated Data) — GCM and ChaCha20-Poly1305 provide both confidentiality AND integrity in one operation. Without authentication, an attacker can flip bits in ciphertext and you won't know the data was tampered with. Always use AEAD modes in new code.

III
Asymmetric Encryption
RSA, ECC, public/private key pairs, and how they solve key distribution
Public Key

The Key Distribution Problem — Solved by Asymmetry

Asymmetric cryptography (public-key cryptography) uses a mathematically linked key pair: a public key (freely shared with everyone) and a private key (kept secret by owner). Data encrypted with the public key can only be decrypted by the corresponding private key. This elegantly solves key distribution — Alice publishes her public key, anyone can send her encrypted data, only she can decrypt.

The security rests on mathematical trapdoor functions: problems that are easy to compute in one direction but computationally infeasible to reverse. RSA's trapdoor is integer factorization. ECC's is the elliptic curve discrete logarithm problem.

RSA Key Pair Relationship n = p × q  ·  φ(n) = (p−1)(q−1)  ·  e × d ≡ 1 (mod φ(n))

RSA — Rivest–Shamir–Adleman (1977)

Key generation: Pick two large primes p and q. Compute n = p×q (the public modulus). Compute Euler's totient φ(n) = (p−1)(q−1). Choose public exponent e (usually 65537). Compute private exponent d as the modular multiplicative inverse of e mod φ(n).

Encrypt: C = Me mod n. Decrypt: M = Cd mod n. Security: knowing only n (public), factoring it back into p and q is computationally infeasible for large n (2048+ bits).

Key sizes: RSA-1024 broken. RSA-2048 = minimum today. RSA-4096 = recommended for long-term security. RSA is slow — used only to encrypt small data (typically: symmetric keys or hashes for signatures).

ECC — Elliptic Curve Cryptography

ECC achieves equivalent security to RSA with much smaller key sizes by operating on the mathematics of elliptic curves over finite fields: y² = x³ + ax + b. The security comes from the elliptic curve discrete logarithm problem (ECDLP) — given a point P and the result Q = kP, finding k is computationally infeasible.

Key size comparison: RSA-3072 ≈ ECC-256 in security. That's a 12× smaller key for the same protection level, which means dramatically faster operations — critical for TLS handshakes on mobile devices and IoT.

Hashing & Data Integrity
SHA family, collision resistance, salting, and password hashing
Integrity

Hash Functions — One-Way Transformations

A cryptographic hash function takes input of any size and produces a fixed-size output (digest) with four critical properties:

Pre-image resistance: Given hash H, computationally infeasible to find M such that hash(M) = H. Second pre-image resistance: Given M, infeasible to find M' ≠ M with same hash. Collision resistance: Infeasible to find any two distinct M, M' that produce the same hash. Avalanche effect: Changing one bit of input completely changes the output hash.

Hash functions are not encryption — they cannot be reversed (no key). They prove integrity: if you hash a file, transmit it, and the recipient's hash matches, the file was not altered.

Salting — Defeating Rainbow Tables and Precomputed Attacks

A salt is a random value added to each password before hashing. This means two users with the same password get different hashes. Without salting, attackers can precompute a rainbow table — a giant lookup table of hash → password mappings for all common passwords. With unique salts, each hash must be attacked individually.

The salt is not secret — it's stored alongside the hash in the database. Its purpose is uniqueness, not secrecy. The format is typically: $algorithm$cost$salt$hash — bcrypt and Argon2 encode all of this in one string.

V
Key Exchange — DH & ECDH
How two parties establish a shared secret over an insecure channel
Key Agreement

The Diffie-Hellman Miracle (1976)

Whitfield Diffie and Martin Hellman solved one of cryptography's hardest problems: how can Alice and Bob establish a shared secret key over a public channel that an eavesdropper can fully observe — without any prior shared secret? The answer uses the discrete logarithm problem as a mathematical trapdoor.

Diffie-Hellman key exchange Public: prime p, generator g  ·  Alice: a (private), A = ga mod p (public)  ·  Bob: b (private), B = gb mod p (public)  ·  Shared secret: K = Ba mod p = Ab mod p = gab mod p

ECDH — Elliptic Curve Diffie-Hellman

ECDH is the modern, efficient version of DH using elliptic curve mathematics instead of integer arithmetic. The public values are points on an elliptic curve, and the shared secret is another curve point. ECDH with X25519 (Curve25519) achieves excellent security with tiny 32-byte key material and is the preferred key exchange in TLS 1.3, WireGuard, and Signal.

Forward Secrecy (Perfect Forward Secrecy / PFS): If you use ephemeral DH keys (DHE or ECDHE) — new keys generated per session — then compromising the server's long-term private key later does NOT expose past session traffic. Past session keys are gone. This is a fundamental security property that DHE/ECDHE provide and plain RSA key exchange does not.

VI
Digital Signatures & HMAC
Non-repudiation, integrity, authentication — how signing works mathematically
Signatures

Digital Signatures — The Asymmetric Triplet

A digital signature provides three guarantees: Authentication (the signer is who they claim), Integrity (the signed data was not modified), and Non-repudiation (the signer cannot deny signing). Unlike encryption (public key encrypts, private key decrypts), signing reverses the roles: private key signs, public key verifies.

Process: Alice hashes her message (SHA-256), then encrypts the hash with her private key to produce the signature. Anyone with Alice's public key can decrypt the signature, recompute the hash, and verify they match. If they match: message is from Alice (authentication), message is unchanged (integrity), Alice cannot deny it (non-repudiation).

HMAC — Hash-Based Message Authentication Code

HMAC provides message authentication and integrity using a shared symmetric key, not asymmetric keys. Both parties share a secret key K. HMAC = Hash(K ⊕ opad || Hash(K ⊕ ipad || message)). It proves the message came from someone with the shared key and hasn't been modified. Cannot provide non-repudiation since both parties share the same key.

HMAC is used extensively in APIs (AWS Signature v4, JWT HMAC), secure cookies, and TLS's MAC record authentication. Faster than asymmetric signatures — ideal for high-volume message authentication.

Cryptographic Attacks
Brute force, birthday attacks, padding oracles, BEAST, POODLE, and downgrade attacks
Attacks

Attacks Target Implementations, Not Just Math

Most cryptographic attacks in practice don't break the underlying math (breaking AES mathematically is computationally infeasible). They exploit implementation flaws, weak configurations, or padding schemes. Every attack below is the result of real-world misconfigurations you can encounter in pen tests and security audits.

AttackTargetHow It WorksReal ImpactPrevention
Brute Force Keys, passwords Try every possible key/password until correct. Parallelizable with GPUs/ASICs. Defeats weak passwords, short keys (DES 56-bit) Long keys (AES-256), strong passwords, MFA, account lockout
Birthday Attack Hash functions Due to birthday paradox, collisions in an n-bit hash require ~2n/2 operations, not 2n. SHA-1 (160-bit) needs only 280 operations to find a collision. MD5 collisions used to forge CA certificates (2008). SHA-1 collisions by Google (2017) Use SHA-256 or SHA-3 (collision resistance: 2128)
Padding Oracle CBC mode ciphertext Server error messages reveal whether padding is valid. Attacker flips ciphertext bits and observes responses to decrypt ciphertext byte-by-byte without the key. BEAST (2011) attack on TLS 1.0 CBC. Allowed session cookie theft. Use AEAD (GCM) not CBC. Constant-time padding verification. TLS 1.3 removes CBC-based ciphers.
POODLE SSLv3 CBC Padding Oracle On Downgraded Legacy Encryption. Forces downgrade to SSLv3, then uses padding oracle to decrypt session cookies. Any browser/server supporting SSLv3 + TLS fallback was vulnerable (2014) Disable SSLv3 and TLS 1.0/1.1 entirely. Only TLS 1.2+ or TLS 1.3.
Downgrade Attack Protocol negotiation MITM forces client and server to negotiate weaker cipher suite or older protocol version they both support. FREAK (export crypto), LOGJAM (512-bit DH). FREAK: servers still supporting "export" 512-bit RSA = breakable in hours Disable export ciphers. Enforce TLS 1.2/1.3 minimum. Use TLS_FALLBACK_SCSV.
Timing Attack Implementation time Measure time to compare strings or perform operations. Variable-time comparison leaks information about the secret (how many characters matched before mismatch). Password bypass by measuring compare_password() execution time Constant-time comparison (hmac.compare_digest in Python). Never use == for secret comparison.
Nonce Reuse Stream ciphers / GCM Reusing the same nonce+key in AES-CTR or GCM allows key recovery via XOR of two ciphertexts. Used in DUAL_EC_DRBG PRNG backdoor. Sony PS3 ECDSA nonce reuse → private key extracted (2010). Bitcoin nonce reuse attacks. Cryptographically random nonce per message. Use sequence counters. Never reuse nonce+key.
VIII
PKI Architecture
Certificate authorities, trust chains, registration authorities, and the web of trust
PKI

Public Key Infrastructure — Solving the Public Key Binding Problem

Asymmetric encryption solves key distribution but creates a new problem: how do you know that the public key you received actually belongs to the intended party and not to an attacker who intercepted it? PKI solves this by having a mutually trusted third party — the Certificate Authority (CA) — vouch for the binding between a public key and an identity by issuing a digitally signed certificate.

When your browser connects to https://sbi.co.in, it receives SBI's certificate, checks that it was signed by a CA it trusts (DigiCert, GlobalSign, etc.), and verifies the CA's signature. The chain of signatures from a trusted root CA down to SBI's certificate is the certificate chain of trust.

Root CA
Self-signed certificate at top of trust chain. Absolutely trusted. Private key in Hardware Security Module (HSM), offline in a vault. Annually verified. DigiCert, Let's Encrypt, Sectigo are examples.
Intermediate CA
Signed by Root CA. Used day-to-day to sign end-entity certificates. Root stays offline — if Intermediate is compromised, revoke it without touching Root. Creates flexibility.
End-Entity Certificate
The certificate for your domain/server/code. Signed by Intermediate CA. Contains: your public key, domain name, validity period, key usage, and CA's digital signature.
RA — Registration Authority
Handles identity verification on behalf of CA. Checks that domain owner actually controls it (DV), checks organization exists (OV), or verifies individual in person (EV).
CRL — Certificate Revocation List
Published list of revoked serial numbers maintained by CA. Browser downloads and checks. Downside: large files, caching delays (stale for hours/days).
OCSP — Online Certificate Status Protocol
Real-time per-certificate revocation check. Browser queries CA's OCSP responder with the certificate serial. Faster than CRL but privacy concern — CA sees which sites you visit.

Certificate Validation Types — DV, OV, EV

DV (Domain Validation): CA only checks you control the domain (automated DNS or HTTP challenge). Issued in minutes. Let's Encrypt uses DV. Shows padlock but no organization info. Good for most websites.

OV (Organization Validation): CA verifies domain control AND legal existence of the organization (company registration check). Takes 1–3 days. Organization name shown in certificate details.

EV (Extended Validation): Strictest — in-person or notarized identity verification. Previously showed green address bar (removed in 2019 by browsers). Used by banks, payment processors. Certificate SAN shows legal entity name.

💡This creates a complete 3-tier PKI hierarchy from scratch — the same architecture used by enterprise CAs and large TLS deployments. Use for internal labs and portfolio.
  1. 1
    Set Up Directory Structure
    mkdir -p ~/pki/{root-ca,intermediate-ca,server}/{private,certs,csr,crl} chmod 700 ~/pki/root-ca/private chmod 700 ~/pki/intermediate-ca/private # Create serial and index files echo 1000 > ~/pki/root-ca/serial echo 1000 > ~/pki/intermediate-ca/serial touch ~/pki/root-ca/index.txt touch ~/pki/intermediate-ca/index.txt
  2. 2
    Generate Root CA Key and Self-Signed Certificate
    # Root CA private key — 4096-bit RSA (will be kept offline in real deployments) openssl genrsa -aes256 -out ~/pki/root-ca/private/ca.key.pem 4096 chmod 400 ~/pki/root-ca/private/ca.key.pem # Self-sign the Root CA certificate (valid 20 years — long for root) openssl req -key ~/pki/root-ca/private/ca.key.pem \ -new -x509 -days 7300 \ -sha256 -extensions v3_ca \ -out ~/pki/root-ca/certs/ca.cert.pem \ -subj "/C=IN/ST=Maharashtra/O=MyOrg Root CA/CN=MyOrg Root CA" # Verify the root certificate openssl x509 -in ~/pki/root-ca/certs/ca.cert.pem -noout -text
  3. 3
    Generate Intermediate CA (Signed by Root)
    # Intermediate CA key openssl genrsa -aes256 -out ~/pki/intermediate-ca/private/intermediate.key.pem 4096 # Intermediate CSR openssl req -new -sha256 \ -key ~/pki/intermediate-ca/private/intermediate.key.pem \ -out ~/pki/intermediate-ca/csr/intermediate.csr.pem \ -subj "/C=IN/ST=Maharashtra/O=MyOrg/CN=MyOrg Intermediate CA" # Root CA signs the Intermediate CA certificate openssl ca \ -config openssl-root.cnf \ -extensions v3_intermediate_ca \ -days 3650 -notext -md sha256 \ -in ~/pki/intermediate-ca/csr/intermediate.csr.pem \ -out ~/pki/intermediate-ca/certs/intermediate.cert.pem
  4. 4
    Issue a Server Certificate (Signed by Intermediate)
    # Server private key openssl genrsa -out ~/pki/server/private/server.key.pem 2048 # Server CSR with SANs (Subject Alternative Names — required by modern browsers) openssl req -new -sha256 \ -key ~/pki/server/private/server.key.pem \ -out ~/pki/server/csr/server.csr.pem \ -subj "/C=IN/ST=Maharashtra/O=MyOrg/CN=app.myorg.internal" \ -addext "subjectAltName=DNS:app.myorg.internal,DNS:*.myorg.internal,IP:192.168.56.10" # Intermediate CA signs the server certificate openssl ca \ -config openssl-intermediate.cnf \ -extensions server_cert \ -days 375 -notext -md sha256 \ -in ~/pki/server/csr/server.csr.pem \ -out ~/pki/server/certs/server.cert.pem # Build the certificate chain (server + intermediate) cat ~/pki/server/certs/server.cert.pem \ ~/pki/intermediate-ca/certs/intermediate.cert.pem > \ ~/pki/server/certs/chain.cert.pem
  5. 5
    Verify the Entire Chain
    openssl verify \ -CAfile ~/pki/root-ca/certs/ca.cert.pem \ -untrusted ~/pki/intermediate-ca/certs/intermediate.cert.pem \ ~/pki/server/certs/server.cert.pem # server.cert.pem: OK ← chain verification successful

TLS

TLS — Transport Layer Security

TLS (Transport Layer Security, formerly SSL) is the cryptographic protocol that secures HTTPS, email (SMTPS, IMAPS), VPNs, and virtually every other internet-facing service. It provides confidentiality (symmetric encryption of traffic), integrity (MAC on every record), and authentication (certificate verification). TLS 1.3 is the current standard; TLS 1.0 and 1.1 are deprecated.

TLS 1.3 vs TLS 1.2 — What Changed

Removed weak cryptography: TLS 1.3 completely removed RC4, MD5, SHA-1, 3DES, DES, NULL ciphers, EXPORT ciphers, and all static RSA key exchange. Only 5 cipher suites remain, all with forward secrecy and AEAD.

Faster handshake: TLS 1.3 completes in 1 RTT (vs 2 RTT for TLS 1.2). With 0-RTT resumption, returning clients can send data immediately — though 0-RTT has replay attack risks and should be used carefully.

Forward Secrecy mandatory: TLS 1.3 requires ephemeral key exchange (ECDHE). Compromise of server's long-term private key does NOT expose past sessions. TLS 1.2 allowed static RSA (no forward secrecy).

Certificate Lifecycle

Lifecycle

Certificates Have a Lifecycle — Managing It Prevents Outages

Certificate expiry is one of the most common and embarrassing security failures in production environments. A single expired certificate can take down a bank's mobile app, payment gateway, or API. Instagram, Microsoft Teams, and Ola have all experienced cert expiry outages. Managing certificate lifecycle requires automation.

Issuance
Generate CSR → submit to CA → domain/identity validation → CA signs and returns cert. For public certs: DV via ACME (Let's Encrypt) takes 30 seconds automated.
Renewal
New CSR + new validation. Max validity 398 days (Apple/Google policy). Automate with certbot, acme.sh, or cloud-native cert managers (ACM, cert-manager for k8s).
Revocation
Invalidate a certificate before expiry (key compromise, misissued, org change). CA adds serial to CRL and updates OCSP responder. Browsers check revocation status.
OCSP Stapling
Server fetches its own OCSP response from CA and staples it to the TLS handshake. Client gets revocation proof without querying CA directly. Solves OCSP privacy issue.
Certificate Transparency
All publicly-trusted certs must be logged in public CT logs. Enables monitoring for unauthorized certificates issued for your domain. Check crt.sh for your domain.
HPKP / CAA Records
CAA DNS records: specify which CAs may issue for your domain. If Let's Encrypt is not in your CAA record, they cannot issue a certificate for you — prevents misissue.

Cryptography in Real Systems

Every tool and protocol you use in security work is built on the primitives you've learned in this module. SSH uses RSA/Ed25519 + ECDHE + AES-256-CTR. HTTPS is X.509 + TLS + AES-GCM. JWTs use HMAC-SHA256 or RSA/ECDSA. GPG uses RSA/ECC. API authentication uses HMAC. Understanding the cryptographic layer underneath these tools lets you make better security decisions and spot misconfigurations.

    SSH Key Types — Why Ed25519 Over RSA

    Post-Quantum Cryptography — Why It Matters Now
    The Quantum Threat: Shor's algorithm (on a large quantum computer) can factor RSA integers and solve ECDLP in polynomial time — breaking RSA and ECC completely. Grover's algorithm weakens symmetric keys: AES-128 becomes ~64-bit effective. Solution: AES-256 remains secure (2^128 Grover complexity). Timeline: "Cryptographically relevant" quantum computer: 10-20 years (est.) "Harvest now, decrypt later" attacks happening NOW: Adversaries store encrypted traffic today to decrypt when QC exists. NIST finalized post-quantum standards in 2024. NIST Post-Quantum Standards (2024): ML-KEM (Kyber) → Key encapsulation (replaces RSA/ECDH) ML-DSA (Dilithium) → Digital signatures (replaces RSA/ECDSA) SLH-DSA (SPHINCS+) → Hash-based signatures (fallback option) Action Today: - Use AES-256 (not AES-128) for long-lived data - Enable hybrid key exchange in TLS (X25519 + Kyber) - Crypto agility: design systems to swap algorithms easily - Inventory certificates and encrypted data stores
