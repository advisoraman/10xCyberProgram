01
Cloud Security Fundamentals
Service models, deployment types, and why cloud security differs from on-prem
Foundation

Why Cloud Security Is Different

On-premises security had a clear perimeter — your firewall was the edge. Cloud dissolves that perimeter. Identity becomes the new perimeter: an attacker with a stolen AWS key has the same access as your admin, regardless of where they are on the planet. Misconfiguration — not malware — is the #1 cause of cloud breaches.

Cloud security requires new skills: understanding IAM policies, recognizing dangerous resource configurations, reading audit logs from APIs instead of network logs, and using cloud-native security tools instead of traditional SIEM-only approaches.

IaaS
Infrastructure as a Service. You manage OS, runtime, apps, data. Provider manages physical hardware, network, hypervisor. AWS EC2, Azure VMs. Most control = most responsibility.
PaaS
Platform as a Service. Provider also manages OS and runtime. You manage app and data. AWS Lambda, Azure App Service, RDS. Less control, less responsibility.
SaaS
Software as a Service. Provider manages everything — you manage data and access. Salesforce, Office 365, Google Workspace. Least control — security focus is configuration and access.
Serverless
Functions as a Service. AWS Lambda, Azure Functions. You write code only; no servers. Security: function permissions, event triggers, secrets in env vars, code vulnerabilities.
Public Cloud
Multi-tenant infrastructure operated by a provider (AWS, Azure, GCP). Most scalable, most feature-rich, but you share physical hardware with other customers (with strong isolation).
Private / Hybrid
Private cloud: dedicated infrastructure. Hybrid: mix of on-prem + cloud. Common in Indian BFSI (RBI data localization) and government. Security spans both environments.

Cloud-Specific Security Risks

Misconfiguration — Public S3 buckets, open security groups, no MFA on root. Easy to create accidentally; catastrophic when exploited. This is #1.

Overprivileged IAM — "Give admin and we'll tighten later" never gets tightened. Compromised overprivileged credentials = full account takeover.

Insecure APIs — Cloud is API-driven. Exposed APIs, weak auth, no rate limiting = cloud-specific OWASP risks.

Insufficient logging — CloudTrail/Activity Logs disabled = forensically blind. Attackers know this and disable logging first.

Supply chain / third-party access — SaaS integrations, CI/CD pipelines with cloud credentials, cross-account roles. Each is a lateral movement path.

Shared Responsibility Model
Who secures what — the foundational concept of all cloud security
Core Concept

The Model in One Sentence

The cloud provider secures "security of the cloud" (the infrastructure). You are responsible for "security in the cloud" (what you put on it). Misunderstanding this is the root cause of many cloud breaches — organizations assume the provider handles things that are actually their responsibility.

Customer Responsibility
Customer data & encryption
Identity & access management (IAM)
OS-level security on EC2/VMs
Network config (Security Groups, NACLs)
Application security & code
Client-side encryption
Firewall config & MFA
Shared (Varies by Service)
Patch management (IaaS: customer; PaaS: provider)
Logging & monitoring setup
Identity federation setup
Encryption key management
Container host OS (EKS/AKS)
AWS/Azure Responsibility
Physical data centre security
Hardware & hypervisor
Global network infrastructure
Availability zones & regions
Managed service security (RDS engine, Lambda runtime)
DDoS protection (Shield Standard)
⚠️ The S3 bucket breach example: AWS secures the S3 infrastructure (hardware, availability, durability). But if YOU set the bucket ACL to "public read," that's YOUR misconfiguration — AWS is not responsible for the breach. This distinction is asked in every cloud security interview.

Real attack paths, OWASP Top 10 for cloud, and common misconfigurations
Threats

How Attackers Compromise Cloud Environments

Cloud attacks rarely start with exploiting vulnerabilities in AWS/Azure itself — the provider's infrastructure is hardened. They start by exploiting customer misconfigurations and credentials. A typical cloud attack chain: find exposed credential (GitHub, env var, metadata service) → enumerate permissions → escalate privileges → establish persistence → exfiltrate data or deploy crypto miners.

AWS IAM Deep Dive
Users, roles, policies, least privilege, and privilege escalation paths
Core AWS

IAM Is the Most Important AWS Security Control

AWS Identity and Access Management (IAM) controls who can do what to which AWS resource. Every action in AWS is an API call, and every API call is evaluated against IAM policies. Get IAM wrong and every other security control can be bypassed by a sufficiently privileged attacker.

IAM has four main components: Users (human identities with long-term credentials), Groups (collections of users sharing policies), Roles (temporary identities assumed by services, Lambda, EC2, or cross-account), Policies (JSON documents defining allow/deny rules).

IAM User
Long-term credentials (access key + secret). Use for human console access. Enable MFA mandatory. Avoid programmatic access keys — use roles instead.
IAM Role
Temporary credentials via STS. Assumed by EC2, Lambda, ECS, cross-account access. Preferred over access keys — credentials auto-rotate, no long-term secret to leak.
Identity Policy
Attached to users/groups/roles. Defines what that identity can do. Managed (AWS or customer) or inline. Identity policies are evaluated per-identity.
Resource Policy
Attached to the resource itself (S3 bucket, SQS queue, KMS key). Controls who can access this resource. Both identity AND resource policies must allow access.
SCPs (Org-level)
Service Control Policies in AWS Organizations. Define the maximum permissions boundary for entire accounts. Even root cannot exceed an SCP deny. Powerful guardrail.
Permission Boundaries
Cap the maximum permissions a user/role can have, even if their attached policies are broader. Used to safely delegate IAM management to developers.

IAM Policy Evaluation Logic

AWS evaluates policies in this order: 1) Explicit Deny (any policy) → immediately denied. 2) Explicit Allow (identity + resource + SCP + boundary) → allowed if all applicable allow. 3) Implicit Deny → default; everything not explicitly allowed is denied.

The key: an explicit Deny anywhere always wins. Use this for security guardrails — a Deny in an SCP cannot be overridden by any identity policy.

S3 Security & Encryption
Bucket policies, ACLs, public access blocks, encryption, and Macie
AWS Storage

S3 — The Most Commonly Misconfigured AWS Service

S3 stores virtually everything in AWS — backups, logs, application data, Terraform state, CI/CD artifacts. A single misconfigured bucket ACL has caused more cloud data breaches than any other configuration error. AWS added account-level "Block Public Access" in 2018 specifically because misconfigured buckets were epidemic.

S3 Access ControlWhat It DoesSecurity Setting
Block Public Access (Account-level)4 settings that override all bucket ACLs and policies to prevent public access. Apply account-wide.Enable ALL 4 settings at account level. Only disable for specific use cases.
Bucket Policy (Resource Policy)JSON policy attached to bucket. Controls cross-account access, enforces HTTPS, restricts source VPC.Deny HTTP (non-TLS), restrict to your VPC via condition: aws:SourceVpc
ACLs (Legacy)Access Control Lists — older mechanism, per-object grants. AWS recommends disabling ACLs and using bucket policies instead.Disable ACLs (bucket ownership = BucketOwnerEnforced)
Presigned URLsTemporary, time-limited URL granting access to a specific object. No credentials needed by recipient.Set short expiry (15 min–1 hr). Use for sharing files instead of making objects public.
Object Lock / VersioningWORM (Write Once Read Many) for objects. Ransomware protection — objects cannot be deleted/modified during retention period.Enable versioning + Object Lock (Compliance mode) for critical buckets.

S3 Encryption Options

SSE-S3: AWS manages encryption keys using AES-256. Simplest. No additional cost. Good for most use cases.

SSE-KMS: Encryption keys managed in AWS KMS. You control key policy, rotation, and usage auditing via CloudTrail. Required for compliance (PCI, HIPAA, DPDP sensitive data).

SSE-C: You provide the encryption key per request. AWS encrypts/decrypts but never stores your key. Highest control, highest complexity.

Client-side encryption: You encrypt before uploading. AWS stores ciphertext only. For maximum sensitivity — even AWS cannot read the data.

VPC Security Architecture
Security Groups, NACLs, VPC Flow Logs, subnets, and network isolation
AWS Network

VPC Is Your Cloud Network Perimeter

A Virtual Private Cloud (VPC) is your isolated network within AWS. You define IP ranges, subnets (public and private), route tables, and internet gateways. All EC2 instances, RDS databases, Lambda functions (if VPC-bound) live inside subnets. Network security in AWS is about controlling what can reach what inside and into the VPC.

Security Groups
Stateful instance-level firewall. Allow rules only (no deny). Automatically allows return traffic. Attached to ENIs (network interfaces). Default: deny all inbound, allow all outbound.
NACLs
Stateless subnet-level firewall. Both allow AND deny rules, evaluated in numbered order. Must explicitly allow return traffic. Applied to entire subnet — blunt instrument.
Public Subnet
Has route to Internet Gateway (IGW). Resources here can get public IPs and be reachable from internet. Use for: load balancers, bastion hosts, NAT gateways only.
Private Subnet
No direct route to IGW. Resources have only private IPs. Use for: EC2 app servers, RDS databases, Lambda, ECS containers. Outbound internet via NAT Gateway.
VPC Flow Logs
Logs all network traffic metadata (IP, port, protocol, accept/reject). Not packet content — like netflow data. Critical for incident investigation. Send to CloudWatch or S3.
VPC Endpoints
Private connectivity to AWS services (S3, DynamoDB, STS) without traversing the internet. Keeps traffic within AWS network. Gateway endpoints (free) vs Interface endpoints.

CloudTrail & AWS Logging
Audit logs, event types, log integrity, and SOC detection queries
Audit Trail

CloudTrail — AWS API Audit Log

AWS CloudTrail records every API call made in your AWS account — who did what, when, from where, to which resource, and what the result was. This is your primary forensic tool for cloud incidents. Without CloudTrail enabled and stored securely, you are forensically blind to cloud incidents.

CloudTrail captures three event types: Management events (control plane — creating EC2, modifying IAM, enabling S3 versioning — on by default), Data events (data plane — S3 GetObject, Lambda invocation — off by default, costs extra), Insight events (anomalous API call volumes — off by default).

AWS Detection

GuardDuty — Cloud-Native Threat Detection

AWS GuardDuty is a managed threat detection service that analyzes CloudTrail, VPC Flow Logs, DNS logs, EKS audit logs, S3 access logs, and Lambda logs — without you having to configure anything. It uses ML + threat intelligence feeds to surface findings. One click to enable; no agents needed.

AWS Security Hub aggregates findings from GuardDuty, Macie, Inspector, IAM Access Analyzer, and third-party tools into a single dashboard. It also runs continuous checks against CIS AWS Foundations Benchmark and AWS Security Best Practices standards.

Azure AD / Microsoft Entra ID
RBAC, Conditional Access, PIM, and identity security in Azure
Azure Identity

Azure Identity Is Different from AWS IAM

Azure Active Directory (now Microsoft Entra ID) is the identity backbone of Azure — and also a standalone enterprise identity platform used by millions of companies for SSO, MFA, and device management. Unlike AWS IAM (pure cloud), Azure AD also integrates with on-premises Active Directory, making it critical for hybrid environments.

Azure uses RBAC (Role-Based Access Control) instead of JSON policies. You assign built-in roles (Owner, Contributor, Reader) or custom roles to users/groups at different scopes (Management Group > Subscription > Resource Group > Resource).

Owner
Full access to all resources AND can manage access. Assign only when absolutely necessary. Minimum viable: use Contributor.
Contributor
Full access to all resources but cannot change access assignments. Good for engineers who need to deploy/manage resources.
Reader
View all resources, read all configs, but cannot make any changes. Good for auditors, monitoring tools, read-only service accounts.
Conditional Access
Azure AD policy engine. "If user is external + accessing sensitive app + from non-managed device → require MFA + compliant device." Zero Trust enforcement.
PIM — Privileged Identity Management
Just-in-time privileged access. Users request elevated permissions for a limited time window. Eliminates standing admin access. Requires Azure AD P2.
Identity Protection
ML-based risk detection: impossible travel, leaked credentials, anonymous IP, malware-linked IP. Automatically enforces MFA or blocks sign-ins when risk detected.

CSPM Lab

What is CSPM?

Cloud Security Posture Management (CSPM) tools continuously scan your cloud environment for misconfigurations, compliance violations, and security risks — automatically, without manual checklist work. They compare your config against benchmarks (CIS, NIST, SOC 2, ISO 27001, DPDP control objectives) and report findings with severity and remediation steps.

Prowler is the leading open-source CSPM for AWS, Azure, and GCP. ScoutSuite is another open-source tool with excellent multi-cloud reporting. Both run against your cloud APIs using read-only credentials — they don't touch your workloads.

Container & Kubernetes Security
Docker security, image scanning, EKS/AKS hardening, and runtime protection
Containers

Container Security Attack Surface

Containers are the dominant cloud workload deployment model. Security risks span four layers: Image (vulnerable packages, hardcoded secrets, running as root), Registry (public images with malware, unsigned images, no scanning), Runtime (privileged containers, capabilities abuse, container escape), and Orchestration (Kubernetes RBAC misconfiguration, exposed API server, etcd without auth).

Trivy — Image Scanning
Open-source vulnerability scanner for container images, filesystem, git repos, IaC. Finds CVEs in OS packages and application dependencies. Free, fast, CI/CD-ready.
Dockerfile Best Practices
Non-root USER, minimal base image (distroless/alpine), no secrets in ENV or layers, multi-stage builds to reduce attack surface, read-only filesystem.
Kubernetes RBAC
Roles + RoleBindings. Principle of least privilege: no cluster-admin for app accounts. Namespace isolation. Avoid wildcard permissions (* verbs).
Pod Security
Pod Security Standards: Restricted/Baseline/Privileged. Deny privileged containers, hostPID/hostNetwork, hostPath mounts. OPA Gatekeeper / Kyverno for policy enforcement.
Secrets Management
Never store secrets in ConfigMaps. Use Kubernetes Secrets (base64, not encrypted by default!) + enable etcd encryption at rest + use AWS Secrets Manager/Vault via CSI driver.
Falco — Runtime Security
CNCF runtime security tool. Detects abnormal container behavior in real-time: shell spawned in container, unexpected network connection, sensitive file read. Sends alerts to SIEM.
