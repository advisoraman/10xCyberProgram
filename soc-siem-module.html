SOC Structure & Roles
What a SOC is, who does what, and where you fit in
Foundation

What is a SOC?

A Security Operations Center (SOC) is a team responsible for monitoring, detecting, and responding to security threats in real time — 24/7. Think of it as the nerve center of an organization's security.

The SOC ingests logs from every system (servers, endpoints, firewalls, apps), feeds them into a SIEM, and analysts watch for anything suspicious.

SOC L1 Analyst
Triage alerts, classify true/false positives, escalate incidents. Entry-level. Your target role.
SOC L2 Analyst
Deeper investigation, threat hunting, handles escalations from L1.
SOC L3 / Threat Hunter
Proactively hunts for threats, builds detection rules, incident commander.
SIEM Engineer
Manages SIEM infra, writes rules, tunes alerts, onboards log sources.
Incident Responder
Handles confirmed breaches, containment, forensics, recovery.
SOC Manager
Oversees team, metrics (MTTD, MTTR), escalation procedures, client reporting.
💡 For your job search: SOC L1 roles in India (TCS, Wipro, Infosys Cyber, KPMG, Deloitte MSSPs) expect you to know log analysis, basic SIEM navigation, Windows Event IDs, and incident triage. That's exactly what this module covers.

Log Sources & Types
Where logs come from and why each one matters
Theory + Lab

Why Logs Are Everything in a SOC

Logs are digital footprints — every action a system takes gets written somewhere. A SOC analyst's job is to read those footprints and spot the ones that don't belong. No logs = blind SOC.

Log sources are categorized by what generates them. Each has different formats, retention requirements, and attack signals to look for.

Log SourceWhat It RecordsKey Attacks to DetectFormat
Windows Event Logs Logins, process creation, user changes, policy changes Brute force, privilege escalation, lateral movement EVTX / XML
Linux Syslog/Auth SSH logins, sudo usage, service starts/stops, cron jobs SSH brute force, backdoors, persistence via cron Plain text
Firewall Logs Allowed/denied connections, source IP, destination port Port scans, C2 beaconing, data exfiltration Syslog / CEF
Web Server (Apache/Nginx) URL requests, status codes, user-agent, source IP SQLi attempts, LFI, brute force, web shell upload Combined Log Format
DNS Logs DNS queries and responses per host DNS tunneling, DGA domains, C2 beaconing Syslog / JSON
Endpoint (EDR) Process trees, file changes, network connections per process Malware execution, persistence, lateral movement JSON / proprietary
VPN / Auth Logs Remote login success/failure, IP geolocation Credential stuffing, impossible travel attacks Syslog
🔬 Lab 2.1 — Manually read Linux auth logs and identify failed SSH attempts LAB ▶
  1. 1
    Open the auth log on your Linux VM
    This file records all authentication events — SSH logins, sudo, su commands.
    cat /var/log/auth.log | grep "Failed password"
  2. 2
    Count failed attempts per source IP
    This helps identify brute force sources quickly.
    grep "Failed password" /var/log/auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head -20
    # Output: count IP_address — high count = brute force candidate
  3. 3
    Check successful logins after failures (sign of success)
    An IP that failed 100 times and then got "Accepted" is a confirmed breach.
    grep "Accepted password" /var/log/auth.log grep "Accepted publickey" /var/log/auth.log
  4. 4
    Check for root login attempts
    grep "root" /var/log/auth.log | grep "Failed"
    ⚠️ Direct root SSH brute force is a critical finding. In a real SOC, this triggers a P1 alert immediately.

Windows Event IDs for SOC
The IDs every L1 analyst must know cold
Must Know

How Windows Logging Works

Windows stores events in Channels (Security, System, Application, PowerShell). Each event has an Event ID that tells you exactly what happened. The Security channel is the most important for SOC work.

You view these in Event Viewer (GUI) or query them with wevtutil / PowerShell (for automation/SIEM ingestion).

Event IDWhat It MeansSOC Significance
4624 Successful account logon Baseline normal activity — watch for unusual hours, Logon Type 3/10
4625 Failed account logon Many failures = brute force. Check Sub Status code for reason.
4648 Logon using explicit credentials Pass-the-Hash, credential reuse — suspicious in most contexts
4672 Special privileges assigned Admin/SYSTEM rights granted — always investigate
4688 New process created Watch for cmd.exe, powershell.exe, wscript.exe spawned by Office apps
4698 Scheduled task created Common persistence mechanism — attackers love Task Scheduler
4720 User account created Unauthorized account creation = attacker establishing foothold
4732 User added to security group Adding to Administrators group is a critical finding
4776 NTLM credential validation Heavy NTLM failures signal Pass-the-Hash or hash spraying
7045 New service installed Malware often installs as a service for persistence

Logon Types — Critical for 4624 / 4625

Type 2 — Interactive
Local keyboard login. Normal at workstations.
Type 3 — Network
File share, SMB access. Watch for lateral movement.
Type 10 — RemoteInteractive
RDP login. Always scrutinize source IP.
Type 5 — Service
Service account login. Baseline, but watch for changes.
💻 Lab 3.1 — Query Windows Event Logs with PowerShell CMD ▶
  1. 1
    Open PowerShell as Administrator on your Windows VM
    Press Win+X → Windows PowerShell (Admin)
  2. 2
    Get last 20 failed login attempts (Event ID 4625)
    Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625} -MaxEvents 20 | Select-Object TimeCreated, Message | Format-List
  3. 3
    Find all process creation events (4688) in last 1 hour
    Get-WinEvent -FilterHashtable @{ LogName='Security'; Id=4688 StartTime=(Get-Date).AddHours(-1) } | Select-Object TimeCreated, @{N='Process';E={$_.Properties[5].Value}}, @{N='ParentProcess';E={$_.Properties[13].Value}}
  4. 4
    Hunt for suspicious: powershell.exe spawned by WINWORD.EXE
    A classic macro malware execution pattern. Look in the results for any powershell.exe or cmd.exe whose parent process is a Microsoft Office application.
    ⚠️ Red flag: WINWORD.EXE → cmd.exe → powershell.exe is a textbook malicious macro chain. Escalate immediately as P1.

Sysmon Deep Dive
Microsoft's free telemetry supercharger for Windows
Tool + Lab

Why Sysmon?

Default Windows logging is limited. Sysmon (System Monitor) adds ~30 event types that Windows natively doesn't log — network connections per process, DLL loading, file creation with hashes, registry changes, and more. It's free, from Microsoft Sysinternals, and used by almost every enterprise SOC.

Sysmon Event IDWhat It CapturesWhy SOC Cares
1Process creation with full command line + parentBest process visibility. Catches LOLBins, encoded PS, malware
3Network connection per processDetect C2 beaconing, reverse shells, data exfil
7DLL loaded by processDLL hijacking, process injection detection
8CreateRemoteThread — code injected into another processClassic malware injection technique
11File created (with hash)Track dropped malware, correlate file hashes with VirusTotal
13Registry value setPersistence via Run keys, UAC bypass, malware config
22DNS query made by processDetect DGA domains, C2 DNS lookups, DNS tunneling

Linux Log Locations

Linux logs live in /var/log/. They're plain text — readable with cat, grep, awk, sed. No GUI needed. Most SOC work on Linux logs is command-line.

Log FileContentsKey Patterns to Grep
/var/log/auth.logSSH, sudo, su, PAM logins"Failed password", "Invalid user", "sudo:", "BREAK-IN"
/var/log/syslogKernel, daemon, cron, general systemcron entries, service crashes, kernel errors
/var/log/kern.logKernel messages onlyiptables drops, hardware errors, module loads
/var/log/apache2/access.logWeb requests — IP, URL, status, sizeSELECT, UNION, ../etc/passwd, .php?cmd=, 500 errors
/var/log/apache2/error.logApache errorsPHP errors, file not found, permission denied
/var/log/cronScheduled job executionsUnexpected entries, unusual scripts, @reboot jobs
/var/log/wtmp (binary)Login historyUse: last command to read
🔬 Lab 5.1 — Detect SQLi and LFI attempts in Apache access logs LAB ▶
  1. 1
    Generate test attacks against your DVWA lab (from Kali)
    Run a few manual SQLi and LFI requests in your browser against DVWA, then analyze the DVWA container logs.
  2. 2
    Search for SQLi indicators in access logs
    grep -iE "(union|select|insert|drop|exec|xp_|%27|%22|'--|;--)" /var/log/apache2/access.log
  3. 3
    Find Local File Inclusion (LFI) attempts
    grep -iE "(\.\./|etc/passwd|etc/shadow|proc/self|\.\.%2F)" /var/log/apache2/access.log
  4. 4
    Find top attacker IPs by request count
    awk '{print $1}' /var/log/apache2/access.log | sort | uniq -c | sort -rn | head -10
  5. 5
    Find all 500 errors (server errors — often SQLi success)
    grep " 500 " /var/log/apache2/access.log | awk '{print $1, $7}' # IP address + URL that caused the 500

Wazuh SIEM — Setup & Operations

What is Wazuh?

Wazuh is a free, open-source SIEM and XDR platform. It collects logs from agents installed on endpoints, normalizes them, runs detection rules, and raises alerts. It also does File Integrity Monitoring (FIM), vulnerability detection, and compliance checks.

Architecture: Wazuh Agent (on endpoint) → Wazuh Manager (processes events, runs rules) → Wazuh Indexer (stores data) → Wazuh Dashboard (OpenSearch/Kibana UI).

Splunk SPL Queries
Search Processing Language — the SQL of SIEM work
Practical

SPL Basics

SPL is Splunk's query language. Every query starts with a search (or implicit search), and you pipe | the results through transforming commands. Same mental model as Linux pipes.

Structure: index=main sourcetype=WinEventLog EventCode=4625 | stats count by src_ip | sort -count

SPL CommandPurposeExample
searchFilter events by keyword/fieldindex=main "Failed password"
statsAggregate: count, sum, avg, dc| stats count by src_ip
timechartTime-series aggregation for charts| timechart span=1h count by EventCode
tableSelect fields to display| table _time, src_ip, user, EventCode
sortOrder results| sort -count
whereFilter after aggregation| where count > 50
rexExtract fields using regex| rex "IP=(?<src_ip>\d+\.\d+\.\d+\.\d+)"
evalCreate computed fields| eval severity=if(count>100,"HIGH","LOW")
🔍 Lab 7.1 — SOC detection queries in Splunk Free SPL ▶
ℹ️Install Splunk Free on your Ubuntu VM. Download from splunk.com. Use port 8000 for the web UI. Ingest your auth.log and/or Windows event logs.
  1. 1
    Detect SSH brute force — IPs with 10+ failed logins
    index=main sourcetype=linux_secure "Failed password" | stats count by src_ip | where count > 10 | sort -count | rename count as failed_attempts
  2. 2
    Detect Windows account lockouts (Event ID 4740)
    index=windows EventCode=4740 | stats count by TargetUserName, SubjectUserName, _time | sort -_time
  3. 3
    Detect suspicious process spawning (powershell from Office)
    index=windows EventCode=4688 NewProcessName="*powershell*" ParentProcessName IN ("*WINWORD*", "*EXCEL*", "*OUTLOOK*") | table _time, ComputerName, ParentProcessName, NewProcessName, CommandLine
  4. 4
    Build a timechart of failed logins over 24 hours
    index=main sourcetype=linux_secure "Failed password" earliest=-24h | timechart span=1h count by src_ip limit=5
    Save this as a Dashboard panel: "Failed SSH Logins Last 24h". Spike = brute force in progress.

Alert Triage Workflow
How a SOC L1 analyst works an alert from start to finish
Core Skill

The L1 Analyst's Job in 1 Sentence

You get an alert. You determine: Is this real? How bad? What do I do? Everything else is procedure around those three questions.

Alert Triage Flow
Alert fires in SIEM
→
Read alert context
→
Gather evidence
→
True Positive?
→
Escalate / Document / Close

True Positive vs False Positive

True Positive (TP)
Real attack or policy violation. Needs escalation and IR. Document everything.
False Positive (FP)
Legitimate activity that triggered a rule. Close the ticket, tune the rule so it doesn't repeat.
True Negative (TN)
No alert, no attack. Normal. Goal is max TNs.
False Negative (FN)
Real attack, no alert. Worst case. Fixed by improving detection coverage.

  2. 2
    Alert appears in Wazuh — read the alert card

  3. 3

MITRE ATT&CK Framework
Map attacker behavior to tactics and techniques
Framework

What is MITRE ATT&CK?

MITRE ATT&CK is a knowledge base of Tactics, Techniques, and Procedures (TTPs) used by real threat actors — documented from real-world attacks. It's a common language for SOC teams to describe attacker behavior.

Tactic = The goal (e.g., Persistence). Technique = How they do it (e.g., T1053 — Scheduled Task). Sub-technique = More specific version (e.g., T1053.005 — Windows Task Scheduler).

TacticWhat Attacker WantsExample Techniques
ReconnaissanceLearn about targetT1595 Active Scanning, T1596 Search Open Sources
Initial AccessGet a footholdT1566 Phishing, T1190 Exploit Public-Facing App
ExecutionRun attacker codeT1059 Command & Scripting, T1204 User Execution
PersistenceSurvive rebootsT1053 Scheduled Task, T1547 Registry Run Keys
Privilege EscalationGet admin/SYSTEMT1548 Abuse Elevation Control, T1055 Process Injection
Defense EvasionAvoid detectionT1070 Indicator Removal, T1562 Impair Defenses
Lateral MovementSpread across networkT1021 Remote Services (RDP, SMB), T1550 Pass-the-Hash
ExfiltrationSteal dataT1041 Exfil over C2, T1048 Exfil via Alternative Protocol
Command & ControlCommunicate with malwareT1071 Application Layer Protocol, T1132 Data Encoding

Incident Response — NIST SP 800-61
The standard IR lifecycle every SOC follows
Critical

NIST IR Lifecycle — 4 Phases

NIST SP 800-61 defines the gold standard for incident response. Every SOC, regardless of size, follows some version of this. As an L1 analyst you operate mostly in Detection and Containment.

Phase 1 — Preparation
Build playbooks, IR policies, tool stack, escalation matrix. Done before incidents happen.
Phase 2 — Detection & Analysis
Alert fires → triage → classify → determine scope. Your primary L1 job.
Phase 3 — Containment, Eradication & Recovery
Isolate affected systems. Remove malware. Restore from clean backups. Primarily L2/L3.
Phase 4 — Post-Incident Activity
Lessons learned meeting. Update playbooks. Improve detection rules. Root cause analysis.

Malware Awareness for SOC
Types, IOCs, and basic static/dynamic analysis
Theory + Tool

Malware Types You Must Recognize

You won't reverse-engineer malware as an L1 — that's malware analysts. But you need to recognize behavioral signatures in logs and alerts to identify what type of malware you're dealing with.

TypeBehavior in LogsKey IOCs to Hunt
RAT (Remote Access Trojan)Outbound connections to uncommon IPs, periodic beaconing, PowerShell spawningC2 IPs/domains, beacon intervals, unusual process network activity
RansomwareMass file renames (.encrypted ext), shadow copy deletion (vssadmin), high disk I/Ovssadmin.exe delete, bcdedit.exe, .locked/.encrypted extensions
KeyloggerProcess writing to unusual files, clipboard access, low-level keyboard hooksUnusual files in %TEMP%, startup registry entries
RootkitHidden processes, hidden files, BSOD on AV scan, API hookingDiscrepancies between process list and raw disk scan
TrojanDisguised as legitimate software, installs backdoor silentlyHash mismatch on known files, unexpected parent processes
WormRapid lateral spread via SMB/RDP, port scanning activity from endpointMass outbound connection attempts, Event ID 4776 failures across multiple hosts
